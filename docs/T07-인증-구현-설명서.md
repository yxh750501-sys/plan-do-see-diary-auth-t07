# T07 인증 구현 설명서

검사 대상 소스는 T06 제출 커밋 `88778c3f9b3d20880c5a2d428abfe01b481eebf5`를 조상으로 둔 T07 소스입니다. 아래 요청·응답은 `npm run build && npm run check && node tests/integration.mjs`로 실행한 **로컬 임시 DB 검사**입니다. 공개 배포와 실제 5일 사용 결과는 별도로 확인해 갱신합니다. 모든 아이디는 합성 계정이며 비밀번호·세션 값의 원문은 기록하지 않았습니다.

## ① 무엇으로 붙였나

- 방식: 자체 서버 인증 흐름에 검증된 라이브러리 `bcryptjs 3.0.3`을 사용했습니다. 비밀번호 저장 방식은 **bcrypt, 비용 12**입니다.
- 로그인 유지: 서버 DB `sessions` 표에 저장하는 **세션**입니다. 브라우저에는 무작위 256비트 값의 `HttpOnly; Secure; SameSite=Lax` 쿠키를 보냅니다. DB에는 해당 값의 SHA-256 해시와 만료 시각을 저장합니다.
- 세션 만료: 발급 후 **7일**입니다. 로그아웃 때 해당 세션을 지우고, 비밀번호 변경 때 그 계정의 모든 세션을 지웁니다. URL에는 세션 값을 넣지 않습니다. 고정 서명 비밀키를 쓰지 않습니다.
- 첫 화면 `/`은 공개 로그인 화면이며, `/diary`와 모든 자료 API는 서버에서 세션을 검사합니다.

## ② 왜 골랐나

`bcryptjs`는 직접 비밀번호 변환 알고리즘을 작성하지 않아도 계정마다 무작위 salt가 붙은 해시를 만들 수 있고, 현재 Worker 빌드에 함께 묶어 실행할 수 있어 골랐습니다. 세션을 서버 DB에 두면 로그아웃과 비밀번호 변경 시 바로 폐기할 수 있습니다. 검토한 다른 방법은 외부 인증 서비스였습니다. 가입·비밀번호 저장값·세션 폐기 장면을 이 과제의 소스와 DB에서 직접 대조하기 어려워 이번에는 채택하지 않았습니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 소스 | 서버 처리 |
| --- | --- | --- |
| 가입 | `src/auth.html`, `src/auth.js`, `worker/auth.js` | `POST /api/auth/signup`: 아이디 중복 검사 → bcrypt 해시 → `users` 저장 → 세션 쿠키 발급 |
| 로그인 | `src/auth.js`, `worker/auth.js` | `POST /api/auth/login`: bcrypt 비교 → 같은 오류 문구로 실패 처리 → 세션 저장 |
| 로그아웃 | `src/private.js`, `worker/auth.js` | `POST /api/auth/logout`: 서버 `sessions` 행 삭제 → 쿠키 만료 |
| 자료 조회 | `worker/index.js`, `src/app.js` | `GET /diary`와 `/api/snapshot` 등에 세션 검사; 계획의 `owner_id`와 연결 관계로 목록 필터 |
| 자료 변경 | `worker/index.js` | 계획·할 일·실행 기록의 ID를 조회할 때 소유자 ID를 함께 검사. 다른 계정의 ID는 404 |
| T06 이관 | `worker/import.js`, `src/private.js` | 로그인한 계정에서 T06 JSON을 검증하고 ID를 다시 매핑해 그 계정 소유로 저장 |
| 5일 사용 | `worker/daily.js`, `src/private.js` | 서울 날짜별 1건, 2일차 뒤·3일차 앞 규칙 변경, 같은 지표·단위 합계와 평균 |

스키마는 `db/schema.ts`와 `drizzle/0001_daffy_captain_marvel.sql`에 있습니다. 기존 T06 자료에는 소유자 열이 없으므로 새 사이트에서 계정 가입 후 가져옵니다. 기존 T06 공개 원본은 가져오기로 자동 삭제되지 않습니다.

## ④ 안 열리는 것을 확인한 기록

로컬 검사에서 합성 계정 A·B의 비밀번호와 쿠키는 파일에 쓰지 않았습니다. 아래의 `[가림]`은 실제 요청 때만 메모리에 있던 값입니다. 요청·응답의 본문도 개인정보가 없는 합성값으로 작성했습니다.

| 확인 | 성공 요청 → 응답 | 거절 요청 → 응답 |
| --- | --- | --- |
| 로그인 없이 자료 조회 | `GET /api/snapshot`, `Cookie: pds_session=[가림:A]` → **200**, A의 계획 1건 | 같은 `GET /api/snapshot`, 쿠키 없음 → **401** `로그인이 필요합니다.` |
| 로그인 안내 동일 | `POST /api/auth/login`, 합성 A 아이디·비밀번호 `[가림]` → **200**, 세션 쿠키 발급 | 같은 주소·방식에서 비밀번호 틀림 → **401** `아이디 또는 비밀번호가 올바르지 않습니다.`; 없는 아이디도 **401**로 같은 문구 |
| 로그아웃 뒤 같은 세션 | `GET /api/snapshot`, `Cookie: pds_session=[가림:A]` → **200** | `POST /api/auth/logout` 후 같은 `GET /api/snapshot`와 같은 쿠키 → **401** `로그인이 필요합니다.` |
| 남의 계획 수정 | `PATCH /api/plans/{B의 계획 ID}`, B 세션 → **200** | 같은 주소·방식과 본문, A 세션 → **404** `계획을 찾을 수 없습니다.`. 반대 방향도 **404** |
| 남의 할 일 삭제·목록 | `DELETE /api/tasks/{B의 할 일 ID}`, B 세션 → **200**; B의 목록에 B 자료만 표시 | 같은 주소·방식, A 세션 → **404** `할 일을 찾을 수 없습니다.`. A의 목록·내보내기에 B 자료 0건, 반대 방향도 0건 |

같은 임시 비밀번호를 쓴 합성 계정 A와 B의 **로컬 검사 DB 저장값**은 아래와 같습니다. 입력 비밀번호는 실행 때 무작위로 생성해 메모리에서만 사용했고 기록하지 않았습니다. 두 해시에 같은 입력을 각각 비교한 결과가 모두 `true`였으며, 해시 문자열끼리는 서로 달랐습니다.

```text
A password_hash = $2b$12$7qLMonuoAk4ktPMQzlxqLufZwCQFHgrBo.2efDW/IgwFpIpZgWPu6
B password_hash = $2b$12$DbEIXsHX8t.DcEge619dAemLVFBKPbe.0/Ht20v2dijh/FUnSixmG
sameInputVerified = true
```

이는 실제 사용자 계정의 저장값이 아닙니다. 로그인 요청·응답 기록에는 비밀번호 원문을 포함하지 않았고 서버 코드는 그 값을 출력하지 않습니다.

## ⑤ AI와 나

- AI에게 맡긴 일: T06 소스를 잇는 인증·계정별 DB 격리·5일 기록 기능 구현과 합성 계정 보안 검사를 맡겼습니다.
- 내가 직접 판단한 일: 사용할 계정의 아이디·비밀번호와 1일차 질문·지표·계획 규칙, 실제 5일의 값은 앱에서 직접 결정하고 입력합니다. 이 항목은 아직 실사용 전입니다.
- AI 제안을 따르지 않은 일: 아직 별도로 거절한 구현 제안은 없습니다. 합성 시계의 5일 결과를 실제 사용 기록으로 취급하지 않았습니다.

## ⑥ 아직 못 막은 것

- 아이디별 또는 IP별 로그인 시도 횟수 제한을 아직 넣지 않았습니다. 공개 로그인 화면에서 무차별 대입 시도가 반복될 수 있습니다.
- 비밀번호 재설정과 두 번째 인증 수단이 없습니다. 비밀번호를 잃으면 계정 복구가 어렵고, 비밀번호가 노출되면 추가 보호 단계가 없습니다.
- **T06 공개 사이트의 원본 기록은 이관만으로 비공개가 되지 않습니다.** T07 계정에 복사한 기록은 격리되지만 원본을 계속 공개하면 같은 내용을 다른 곳에서 볼 수 있습니다. T06 제출용 공개 주소를 어떻게 유지할지 결정한 뒤 원본 접근을 정리해야 합니다.

## 실제 5일 사용 상태

로컬 검사는 합성 시계로 5일·규칙 변경·합계/평균을 검증했으며 실제 계정의 사용 기록을 대신하지 않습니다. 공개 앱에서 본인이 1일차 질문과 지표를 고정하고 서로 다른 서울 날짜 5일을 기록해야 이 절을 실제 결과로 채울 수 있습니다.
